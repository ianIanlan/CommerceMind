# CommerceMind 阶段级性能优化 v1

## 目标

此前端到端报告只能看到总耗时，无法回答慢在记忆、意图、Agent、工具还是最终合成。本轮先加入
阶段级 Trace，再依据真实瓶颈做最小优化。

测试日期：2026-09-27。环境与场景和 `interview_evidence_v1` 相同，使用 Docker 全栈和
`deepseek-flash`。以下均为固定场景的单次实测，受模型网关波动影响，不代表稳定的 P50/P95。

## 基线定位

| 场景 | 总耗时 | 意图识别 | Agent 并行墙钟 | Composer | 记忆读写 |
|---|---:|---:|---:|---:|---:|
| 物流 | 8.98 s | 3.18 s | 5.76 s | 0 | 35.1 ms |
| 重复扣款 | 13.78 s | 3.67 s | 10.09 s | 0 | 24.7 ms |
| 登录 + 重复扣款 | 23.38 s | 6.75 s | 9.96 s | 6.65 s | 24.9 ms |
| 转人工 | 2.26 s | 2.19 s | 37.3 ms | 0 | 30.5 ms |

结论：路由、Guard、Redis/Chroma 记忆读写均不是主要瓶颈。复合请求中的两个领域 Agent 已经
并行执行；额外的 LLM Composer 和显式转人工仍等待 LLM 意图分类，属于可消除调用。

## 修改

1. API 返回并在统一 Trace 中保存 `stage_timings_ms`，包括记忆读取、意图识别、上下文构造、
   编排、路由、Agent 并行墙钟、各 Agent、Composer、Guard、记忆写入和总耗时。
2. Docker 默认使用确定性 Composer：保留主 Agent 原文并以“补充说明”追加辅助结果，避免第三次
   LLM 调用。仍可设置 `COMMERCEMIND_COMPOSER_MODE=llm` 做质量对照。
3. “转人工/人工客服”是低歧义控制指令，使用 Pattern 快速路径，不再等待 LLM；可通过
   `INTENT_PATTERN_FAST_PATH=false` 关闭。
4. 修正 Guard 对“请不要发送验证码”等安全提醒的误报，只拦截真实的敏感数据索取表达。

## 优化后复跑

| 场景 | 优化前 | 优化后 | 单次降幅 | 功能断言 |
|---|---:|---:|---:|---:|
| 物流 | 8.98 s | 8.25 s | 8.1% | PASS |
| 重复扣款 | 13.78 s | 8.24 s | 40.2% | PASS |
| 登录 + 重复扣款 | 23.38 s | 17.38 s | 25.7% | PASS |
| 转人工 | 2.26 s | 46.8 ms | 97.9% | PASS |

复合请求的 Composer 从 6.65 秒降至约 0.1 毫秒；两个 Agent 仍并行，墙钟 10.63 秒，而不是
8.10 秒与 10.62 秒相加。该轮六个端到端场景仍为 6/6 通过。

## 不能得出的结论

- 前后各一次运行不足以证明稳定性能提升，尤其单领域 Agent 延迟受远程模型波动影响。
- 确定性合并减少延迟，但还需要独立盲评比较完整性、重复率和用户偏好，才能决定生产默认值。
- 当前没有供应商 token usage，暂时不能报告准确成本节省。

## 下一轮预注册实验

对同一批固定输入交替运行 `llm` 与 `deterministic` Composer，各至少 10 次，统一报告任务成功率、
回答完整性、重复率、P50/P95、模型调用数和 token 成本。意图识别仍是复合请求的第二大瓶颈，
但不能仅为降延迟把所有业务意图改为规则快速路径；应先扩大冻结集并为高精度快速路径单独测量
precision 和误路由率。
