# CommerceMind 面试讲解手册

这份文档不是功能说明书，而是项目答辩顺序。目标是先讲业务风险和工程决策，再用实验数字证明，不从技术栈清单开始。

## 简历版本

**CommerceMind｜可靠电商客服 Agent 系统**

基于 FastAPI、LLM、Redis、ChromaDB、PostgreSQL 与 Docker Compose，构建覆盖订单、物流、支付和售后的条件式多 Agent 系统；通过工具白名单、两阶段确认、事务幂等与支付结果核对约束高风险操作，并使用真实 AmazonHelp 语料、消融实验、故障注入和并发测试验证意图路由与交易可靠性。

## 30秒开场

> CommerceMind 是我为电商售后设计的可靠 Agent 系统。它和普通客服机器人的区别是，模型只负责理解用户和组织回复，订单事实与写操作都由代码控制。系统会按意图选择订单、账单、售后或技术 Agent，Agent 只能调用白名单工具。退款采用 prepare、用户确认、execute 三阶段，并用数据库事务和支付幂等键避免重复执行；如果支付渠道可能已经成功但响应超时，系统会进入待核对状态，而不是猜测成功或失败。项目用内部回归集、公开 AmazonHelp 真实表达、消融、并发和故障注入做了验证。

## 两分钟讲解

### 1. 为什么做

普通 LLM 客服可以生成流畅回答，但无法保证三件事：引用的订单状态是真实的、没有越权调用工具、重复确认不会产生重复退款。因此项目目标不是让回答更像人，而是让 Agent 在业务约束下安全完成任务。

### 2. 主链路

```text
记忆读取 → 意图识别 → 条件路由 → Agent 执行
→ 白名单工具/RAG → 回复合并与 Guard → 记忆写回 → Trace/Evaluation
```

意图识别以 LLM 为主，Pattern 提供确定性信号和失败兜底。语义 Embedding 只有达到校准阈值时才允许跳过 LLM；由于外部验证覆盖率只有4%，当前默认关闭。

### 3. 为什么是条件式多 Agent

多 Agent 不是默认更好。CommerceMind 只在跨领域问题中调用辅助 Agent，单领域请求保持单 Agent。拆分的核心价值是缩小工具权限和上下文范围，并允许分别评估；代价是路由错误、调用成本和结果合并复杂度。

### 4. 最难的可靠性问题

退款请求不会直接执行。系统先校验订单归属和退款资格，持久化待确认动作；用户确认后才执行。动作和支付渠道都使用稳定幂等键，因此重复点击和并发确认只对应一次业务操作。

支付超时不能简单当失败，因为渠道可能已经提交。CommerceMind 将其记录为 `reconciliation_required`，不写入虚假成功记录，也不告诉用户“退款失败”；后续继续使用原幂等键核对。

### 5. 如何证明

- 104项自动化测试通过。
- 7/7任务级业务状态断言通过。
- 16线程并发确认只执行一次支付调用。
- 55条 AmazonHelp 诊断集从45.45%提升到89.09%。
- 25条零重叠 holdout 为23/25，95%置信区间75.03%–97.78%。
- 真实模型链路并发10时P95为10.7秒，说明第三方模型尾延迟仍是瓶颈。

## 五个核心设计决策

| 决策 | 原因 | 代价或边界 |
|---|---|---|
| LLM理解，代码执行 | 模型输出不可直接作为业务事实 | 需要领域服务和工具契约 |
| 条件式多 Agent | 权限隔离、上下文收敛、可独立评测 | 路由和合并复杂度增加 |
| 高风险动作两阶段确认 | 防止模型或用户误触直接改变状态 | 多一次交互，需要动作过期策略 |
| 稳定幂等键贯穿本地与渠道 | 防止重试和并发造成重复交易 | 渠道必须支持幂等语义 |
| Monitor与Evaluation分离 | 在线健康不等于回答质量 | 需要两套指标和报告 |

## 高频追问

### 为什么不用一个模型加全部工具？

规模小时可以。拆分只有在领域权限、工具集合或评测标准明显不同的时候才有价值。本项目将退款工具限制给售后 Agent，将付款查询限制给账单 Agent；跨领域请求才增加辅助 Agent。这样路由错了也有工具白名单作为第二道边界。

### 规则这么多，还是 Agent 吗？

Agent 的价值在开放语义理解、工具选择和回答组织；交易权限、状态转换与幂等必须是确定性代码。把所有逻辑交给 LLM 不是“更智能”，而是把不可验证的概率判断放进了资金链路。

### LLM confidence 是准确概率吗？

不是。它是模型输出的自评分，只能作为融合证据。项目没有用标注数据做概率校准，因此不会把0.8解释为80%正确率。Embedding 快速路径另外使用阈值和top1-top2 margin校准。

### 为什么 Embedding 默认关闭？

字符向量在真实英文外部集上失效；替换为多语言语义模型后，冻结集高精度快速路由只覆盖4%。它没有造成错误，但降本证据不足，因此保留能力和复现实验，不默认开启。

### 工具白名单只是写在 Prompt 里吗？

不是。每个 Agent 在代码中只注册允许使用的工具。模型产生工具名后，还要经过存在性、所属 Agent、JSON Schema、必填字段和业务权限校验。Prompt 是行为引导，代码才是授权边界。

### 模型伪造“退款成功”怎么办？

最终回复 Guard 会检查高风险结论；更关键的是，真正的退款结果只来自领域服务和渠道返回。模型文本不能修改退款表，也不能生成有效的支付渠道资源 ID。

### 支付超时为什么不能直接重试？

超时只说明没有收到响应，不代表渠道没有执行。系统先进入待核对状态，再使用同一个幂等键请求；即使第一次已经成功，渠道也返回同一业务结果，而不是创建第二笔退款。

### 92%是否代表生产准确率？

不代表。holdout只有25条，标签是单轮审阅的silver label，且数据来自公开社交媒体。它只能作为独立于合成集的补充证据。报告同时给出置信区间和错误样本，没有外推到生产流量。

### RAG、Skills和工具有什么区别？

- RAG提供外部业务知识，例如退货政策。
- Skills提供角色流程和边界，例如售后必须先核验哪些字段。
- 工具读取或改变真实系统状态，例如查询订单、创建待确认动作。

### 项目最大的不足是什么？

外部评测规模小且不是双人金标；订单和支付默认是演示环境；真实模型P95仍高；支付对账缺少异步 webhook 和定时任务；多实例并发还需要用 PostgreSQL 锁重新验证。这些是从工程原型走向生产的下一阶段，不应包装成已完成。

## 演示顺序

如果面试官要求演示，控制在五分钟：

1. 输入物流查询，展示意图、Order Agent、订单与物流工具 Trace。
2. 输入“登录失败并且重复扣款”，展示主辅 Agent 条件并发，而不是所有请求都多 Agent。
3. 发起退款，展示只生成 `awaiting_confirmation`，数据库尚无退款记录。
4. 确认两次，展示相同退款 ID 和单条审计事件。
5. 展示支付超时测试与 `reconciliation_required`，最后打开实验报告说明边界。

不要把时间花在前端样式上，重点展示结构化 Trace、业务状态和失败路径。

## 不要说过头的话

| 避免表述 | 推荐表述 |
|---|---|
| 已达到生产级 | 接近生产架构的可复现工程原型 |
| 保证退款安全 | 约束退款授权、确认、幂等和核对流程 |
| 三路融合一定更准 | 通过消融决定各路径是否启用 |
| 92%生产准确率 | 25条冻结silver-label holdout上23/25 |
| 已接入真实电商系统 | 实现真实接口语义和Stripe Test适配器，默认使用演示数据 |
| 多 Agent 提高了所有请求效果 | 条件式多 Agent主要用于权限隔离和复合问题 |

## 技术栈速记

- 应用：Python 3.12、FastAPI、Pydantic、httpx
- 模型：Anthropic-compatible / OpenAI Responses-compatible LLM
- Agent：条件路由、角色契约、工具调用、动态 Skills、Composer、Guard
- 数据：PostgreSQL/SQLite、Redis、ChromaDB
- 检索：RAG、领域过滤、查询扩展、重排、引用
- 可靠性：事务、幂等、确认状态机、结果核对、超时、熔断、降级
- 工程：Docker Compose、Nginx、Prometheus、pytest、消融与并发压测
