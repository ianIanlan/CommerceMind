# CommerceMind 项目审视与演进路线

## 1. 项目定位

CommerceMind 是一个面向电商售后的可观测 Agent 系统。核心目标不是做一个只会生成客服话术的聊天机器人，而是让模型在受控边界内读取订单事实、调用业务工具、执行高风险动作，并且让整个过程可追踪、可评测、可回归。

## 3. 相比普通客服机器人的提升

1. **回答有业务事实支撑**：订单状态、付款记录和退款资格来自工具，不由模型猜测。
2. **高风险动作可控**：写操作先预检，再由用户确认；幂等键避免重复执行。
3. **权限边界明确**：身份隔离、Agent 工具白名单和参数校验共同限制模型权限。
4. **效果可量化**：意图识别、检索和编排都有独立数据集与消融实验，不只展示几个成功案例。
5. **问题可定位**：trace 能区分意图、检索、路由、工具和生成阶段的问题。
6. **组件可替换**：模型客户端、存储和检索都有接口与本地降级实现，便于演示和迭代。

## 4. 当前边界与风险

- 演示订单库和工具是本地实现，尚未接入真实 OMS、支付和物流系统。
- 离线 Embedding 是轻量回退实现，不等同于生产级语义向量模型。
- 评测数据规模仍小，不能证明对真实长尾流量的泛化能力。
- LLM Judge 只能作为一类评测证据，需要和规则、人工标注及业务指标交叉验证。
- `AUTH_MODE=demo` 只适合本地演示；生产必须使用强身份认证、RBAC 和密钥管理。
- 当前 Docker Compose 面向单机复现，不提供多副本调度、跨机容灾和自动扩缩容。

## 5. 后续优先级

### P0：从“能演示”到“可信工程项目”

- 将数据库变更纳入 Alembic 迁移，去除启动时隐式建表。
- 为模型网关补齐限流、重试预算、熔断指标和失败分类。
- 接入 OIDC/JWT、RBAC 和部署侧 Secret 管理，移除生产默认密码。
- 在 CI 中自动执行单测、前后端构建、Compose 配置校验和核心冒烟测试。
- 扩充人工标注的意图、检索与任务完成数据集，并固化版本化基线。

### P1：增强效果与可解释性

- 使用真实中文 Embedding，构建 BM25 + 向量混合召回，并增加 reranker。
- 建立路由置信度校准和拒识阈值，避免把 LLM 自评分当成真实概率。
- 增加复杂多轮、冲突信息、越权请求、工具故障和提示词注入测试。
- 用 OpenTelemetry 串联 API、模型、检索、数据库和工具调用链路。
- 加入并发压测，给出 P50/P95/P99、错误率、成本与任务成功率。

### P2：贴近真实市场场景

- 以适配器方式接入一个真实或沙箱订单/支付/物流 API。
- 接入工单平台，实现人工接管、上下文摘要和处理结果回流。
- 增加多租户知识库、权限隔离、内容审核和知识版本管理。
- 建立线上反馈闭环：失败聚类、数据标注、离线回归、灰度发布和回滚。

## 6. 项目展示建议

建议把项目描述为“可复现的工程原型”，重点说明三个设计选择：为什么业务事实必须来自工具、为什么高风险动作采用两阶段确认、为什么用消融实验验证多路意图、RAG 和编排。项目尚未宣称达到生产级；当前边界和 P0 到 P2 的演进方案均在本文中明确列出。
