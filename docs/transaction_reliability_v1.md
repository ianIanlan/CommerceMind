# 高风险交易可靠性实验 v1

## 目标

验证模型即使重复确认、并发确认或遇到支付渠道超时，也不能造成重复退款或错误的业务结论。安全性由领域状态机、数据库事务和支付幂等键实现，不依赖 Prompt。

## 状态设计

```text
awaiting_confirmation
        │ 用户确认
        ▼
    executing ───────────────► succeeded
        │
        │ 渠道可能已执行，但响应丢失
        ▼
reconciliation_required
        │ 使用原 action_id 作为相同幂等键核对
        └────────────────────► succeeded
```

`PROVIDER_OUTCOME_UNKNOWN` 与明确失败不同：系统既不写入本地退款成功记录，也不向用户宣称失败。再次核对仍使用原 `action_id`，支付渠道只能对应一个退款操作。

## 自动化证据

- 同一个退款动作重复确认，只生成一个退款记录。
- 16个线程并发确认同一个动作，只调用支付渠道一次。
- 模拟支付渠道已经提交退款但响应超时：首次进入 `reconciliation_required`，第二次使用相同幂等键取得原结果。
- 用户后续提到其他订单，不会改变已经持久化动作绑定的订单和参数。
- 订单在 prepare 与 confirm 之间进入发货状态时，取消动作回滚。
- 其他用户不能读取订单或确认动作。
- 工具 Trace 隐藏完整收货地址。

任务级过程断言为 **7/7 PASS**；全仓库自动化测试为 **104/104 PASS**。

## 边界

- 当前用 MockTransport 和可控 Gateway 注入超时，验证的是本地协议与状态机，不是支付机构生产 SLA。
- Stripe 适配器传递幂等键，但生产还需要异步 webhook、定时对账、告警和人工处置队列。
- SQLite 事务证明单进程语义；多实例部署应使用 PostgreSQL 行锁或 compare-and-set，并再次执行并发测试。
