# CommerceMind 电商售后 Agent 设计基线

## 1. 项目目标

CommerceMind 面向订单、物流、退换货、支付和人工交接场景。项目的目标不是增加 Agent
数量，而是构建一条可验证的业务闭环：

```text
理解请求 -> 补齐字段 -> 查询业务事实 -> 检索适用政策 -> 风险审核
         -> 用户确认 -> 执行动作 -> 审计/人工交接
```

## 2. 设计原则

1. 默认单领域处理，只在明确的复合诉求中进行多领域协作。
2. 订单、支付和退款状态必须来自结构化工具，不能由模型猜测。
3. 政策事实来自带版本的知识库；Skills 只保存稳定流程和边界。
4. 退款等写操作必须经过预检、用户确认、幂等校验和审计。
5. 高风险约束由代码执行；Prompt 和 LLM Judge 只作为补充。
6. 每个结论都应能回放到路由、工具结果、知识证据和审核结果。

## 3. 第一阶段领域模型

- `Product`：商品类别、价格及是否为虚拟商品。
- `Order`：订单所有者、状态、金额和收货信息。
- `Payment`：支付流水、渠道、金额和状态。
- `Shipment`：承运商、运单号和物流轨迹。
- `RefundRequest`：退款申请及处理状态。
- `PendingAction`：等待用户确认的高风险动作。
- `AuditEvent`：所有工具调用和状态变更的审计记录。

## 4. 写操作状态机

```text
READY -> AWAITING_CONFIRMATION -> EXECUTING -> SUCCEEDED
                                     |             |
                                     +-> FAILED    +-> 不允许重复执行
```

退款预检只创建 `AWAITING_CONFIRMATION` 动作；确认接口才允许执行。`idempotency_key`
具有唯一约束，防止重试或并发请求产生重复退款。

## 5. 领域工具

只读工具：

- `get_order`
- `get_logistics`
- `get_payment_records`
- `get_refund_status`
- `check_return_eligibility`

写操作：

- `prepare_refund_request`：预检并生成待确认动作，不执行退款。
- `confirm_action`：确认并执行动作；必须校验用户、状态和幂等键。

## 6. 测试门槛

第一阶段必须验证：

- 用户不能读取他人的订单。
- 虚拟商品不能走普通七天无理由退款。
- 未确认的动作不会创建退款。
- 同一幂等键不能创建两个退款动作。
- 同一动作重复确认不会重复创建退款。
- 重复扣款核验返回支付事实，但不自动判定或执行退款。
- 每次写操作都有审计记录。

后续阶段将补充 Agent 路由、政策版本 RAG、输出审核、Trace 和离线评测。
